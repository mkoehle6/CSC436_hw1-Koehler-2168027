CASE 1 - Connection refused

C:\Users\mlkoe>curl -sS --max-time 8 -v http://127.0.0.1:9/
*   Trying 127.0.0.1:9...
* connect to 127.0.0.1 port 9 from 0.0.0.0 port 39164 failed: Connection refused
* Failed to connect to 127.0.0.1:9 after 2038 ms: Could not connect to server
* closing connection #0
curl: (7) Failed to connect to 127.0.0.1:9 after 2038 ms: Could not connect to server

What happened on the wire
1. A SYN packet was sent from localhost port 39164 to localhost port 9.
2. After receiving the packet, the host checked for a socket listening on port 9, found none,
and sent a RST, ACK packet in return.

Symptoms ruled out
1. The host is down or unreachable. We received a packet from the host.
2. A name resolution problem. DNS is not involved as we have an IP address.
3. Packet filtering on the wire.  Filtering would have dropped the packet.  We received a response.

Command to run next
netstat -ano | findstr :9 - to check whether a process is listening on port 9.

CASE 2 - Connection timed out

C:\Users\mlkoe>curl -sS --max-time 8 -v http://192.0.2.1/
*   Trying 192.0.2.1:80...
* Connection timed out after 8015 milliseconds
* closing connection #0
curl: (28) Connection timed out after 8015 milliseconds
 
What happened on the wire
1. A SYN packet was sent to 192.0.2.1.
2. After 1 second passed with no reply, a second SYN packet was sent.
3. A third SYN packet was sent after an additional 2 seconds with no ACK.
4. A fourth SYN packet was sent after an additional 4 seconds with no ACK received.
5. The curl process ended after 8 seconds, as specified by the --max-time flag.

Symptoms ruled out
1. Anything that involves the server or process you are trying to connect to. The host
would have replied with an ACK if it had received the SYN packet.

Command to run next
1. Check that the address is legitimate, with no typos or unintended reserved address.
2. Assuming I have access and administrative privileges on the destination host, check that
the host is powered on and that the operating system is up and running. Next, check whether
a firewall rule is silently dropping incoming packets to the port.

CASE 3 - Reset mid-connection

Terminal 1
PS C:\Users\mlkoe\Downloads> node .\abort-server.mjs
abort server listening on 127.0.0.1:8472
try:  curl -sS --max-time 8 -v http://127.0.0.1:8472/
expect: curl: (56) Recv failure: Connection was reset

Terminal 2
C:\Users\mlkoe>curl -sS --max-time 8 -v http://127.0.0.1:8472/
*   Trying 127.0.0.1:8472...
* Established connection to 127.0.0.1 (127.0.0.1 port 8472) from 127.0.0.1 port 38497
* using HTTP/1.x
> GET / HTTP/1.1
> Host: 127.0.0.1:8472
> User-Agent: curl/8.21.0
> Accept: */*
>
* Request completely sent off
* Recv failure: Connection was reset
* closing connection #0
curl: (56) Recv failure: Connection was reset

What happened on the wire
1. Localhost port 38497 sent a SYN packet to localhost port 8472.
2. Port 8472 replied with a SYN, ACK packet.
3. Port 38497 replied with an ACK packet to establish the connection (the TCP three-way handshake).
4. Port 38497 then sent an HTTP GET request.
5. Port 8472 closed the connection by sending a RST, ACK packet.

Symptoms ruled out
1. Similar to case 1, we know the host is online because it answered.
2. There are no name-resolution issues because we used an IP address.
3. No packet filtering on the wire between source and destination.

Command to run next
Using Windows PowerShell, $LASTEXITCODE will display the error code if it was not displayed.
Other options include checking for a server crash or an expired NAT entry.
